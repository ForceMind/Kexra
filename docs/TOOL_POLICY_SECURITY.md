# 工具策略加载故障边界

开发分支 `codex/tool-policy-fail-closed-20261107` 基于主线 `70a468f87f9531f32ebdc63f0fdeee258d0f8e00`，本轮只修改 guard、Interceptor 与对应回归。它不引入新授权模型或操作系统沙箱，尚未合并/发布。

## 行为契约

已配置拦截器在加载规则或启用工具集合失败时，不能把故障解释为“工具未启用拦截”或“没有规则命中”。`IsToolEnabled` 现在返回 `(bool, error)`，`Match` 返回 `(Decision, bool, error)`；Guard 的两处调用均处理错误并立即返回平台阻断，不进入默认放行或 LLM fallback。

规则编译与启用集合都成功后才发布缓存快照。无效 JSON、`null`、非字符串或 null 数组元素和启用规则中的非法正则均产生策略错误。失败批次不污染有效状态；后续调用会重试，数据库恢复后可正常加载。

以下既有选择保持兼容：

- 启用集合未保存时使用原有默认工具列表。
- 明确保存 `[]` 表示关闭拦截；`SetEnabledTools(nil)` 也序列化为 `[]`，避免产生含糊的 `null`。
- 有效规则的匹配、普通无匹配及用户明确配置的模型 `FailAction=allow` 保持原语义。
- 有效缓存的使用、UI 更新后的 Invalidate 和已有审计格式保持不变；这不是持续重新读取数据库或全局故障开关。

已扫描固定主线全部 174 个生产 Go 文件和 211 个测试文件；这两个接口只有 Guard 的两处生产调用，已同步更新。无数据库结构、环境变量、账号或数据迁移。持久化配置损坏现在会阻止工具执行，管理员应修复配置后重试，不自动把损坏值改为关闭保护。

## 实际验证与限制

新增 `guard/guard_policy_test.go` 使用标准库 `database/sql` 故障驱动提供策略行并注入读取失败；加载、缓存、正则、匹配和 hook 判定均执行真实生产源码。回归覆盖读取失败、损坏/null 配置、非法正则、缓存原子发布、恢复、并发及显式关闭/缺省兼容。

原始主线先运行新增安全用例，成功复现异常放行；修改后，与既有 guard/intercept 用例合计 **49 条测试通过记录（含子例）**，race、vet 与格式检查通过。交付的三个源码/测试文件与实际运行文件逐字节一致。

当前环境缺少完整依赖和 PostgreSQL。上述验证在临时裁剪工程执行：策略源码和官方 SDK hook/LLM 类型保留，DB 初始化与未用到的会话持久化支持被裁剪。它可以验证故障注入路径，但不能替代完整工程编译、真实 SQL/事务、server/Web 或生产集成；裁剪支持和 SDK 副本没有提交到产品源码。

在完整仓库与推荐 Go 1.26.9 环境继续执行：

~~~bash
go test ./guard ./intercept -count=1
go test -race ./guard ./intercept -count=1
go vet ./guard ./intercept
go build ./...
~~~

本轮未调用外部模型、未执行外部资产扫描、未修改真实策略数据，也未触发 Actions。认证 PR #19 的数据库门禁、独立出站修复及供应链 PR #15 保持各自验收范围。其他工具表读取、模型失败处理、出站授权和持久化审批仍需逐项审查；不宣称已消除全部异常放行路径。回退会恢复旧故障边界，不作为安全生产回退。
