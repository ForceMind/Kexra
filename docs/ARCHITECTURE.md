# Kexra 技术架构

## 定位与边界

Kexra 在应用层组织 AI 任务协作和安全发现的管理流程。它是**编排工作台**，不是模型本体；AI 能力依赖所配置的模型 API 和工具。任何结果都需要证据与人工复核。

## 总体构成

~~~text
浏览器（Next.js/React）
    |
    | HTTP API / 实时活动流
    v
Go Web 服务（server/）
    |-- 任务与 Agent 编排（agent/、server/）
    |-- 模型选择与调用（llmpool/、llmrec/）
    |-- 数据访问与持久化（db/、evidence/、report/）
    |-- 扩展与集成（mcphttp/、skills/、notify/）
    |-- 网络与流量管理（traffic/、intercept/、guard/）
    |-- 更新能力（selfupdate/）
    |
    v
PostgreSQL + 本地数据目录
~~~

该图为源码结构的概念示意，不表示所有功能均已完成真实环境验收。

## 模块责任

| 目录 | 主要关注点 |
| --- | --- |
| `cmd/kexra/` | 品牌分支中的 Go 启动入口；需要同步测试与发行验证 |
| `server/` | API、认证、任务交互、实时活动及服务端编排 |
| `agent/` | 规划与执行会话、工具调用和任务收尾 |
| `db/` | 资产、任务、设置及记录的数据库访问 |
| `evidence/` / `report/` | 证据保存、报告生成 |
| `llmpool/` / `llmrec/` | 模型配置选择及调用记录 |
| `mcphttp/` / `skills/` | 外部工具接口与技能描述 |
| `traffic/` / `intercept/` / `guard/` | 流量、拦截、操作审查；不等于隔离沙箱 |
| `web/` | Next.js、React、TypeScript、next-intl、UI 状态 |
| `detections/` | 防御检测规则及测试样例，与运行时产品功能分开维护 |
| `selfupdate/` | GitHub Release 更新逻辑，启用前必须核验目标仓库及包名 |

## 主要数据流

1. 人类确定**合法授权的测试范围和限制**，创建任务。
2. 规划组件根据目标与已有事实协调执行步骤。
3. 执行组件使用已配置工具并产生状态、事实和证据引用。
4. 持久化层保存任务关系、资产与发现；界面消费 API 和事件展示进度。
5. 人类审查发现、审批与报告，并决定是否复测或结束任务。

**技术证据必须保持原样**，不应因中文化或品牌替换修改 HTTP 请求、命令、日志、签名或原始时间线。

## 需要进一步验证的架构风险

- API 授权与工具执行的边界、任务间隔离、出站请求限制、敏感信息遮盖。
- 使用数据库/应用级规则进行拦截并不能替代容器、虚拟机及网络级隔离。
- `selfupdate/` 必须使用新发布源和配套校验文件；当前不应视为可放心执行的升级入口。
- 兼容历史用户、Cookie 与数据库命名，不能把它们当成可随手删除的旧品牌文件。
